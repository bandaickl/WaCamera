## 1. リポジトリーとビルド

一つのリポジトリーに、純Javaの共通部分と二つの独立したMODビルドを置く。

```text
WaCamera/
  core/                    Java 17。経路、時計、録画状態、設定検証
  recorder/                Java 17。FFmpeg管理、フレーム供給、保存処理
  forge-1.20.1/            Forge MDK / ForgeGradle / Java 17
  neoforge-1.21.1/         NeoForge MDK / ModDevGradle / Java 21
  native-audio/windows/    C++。プロセス単位の音声キャプチャー補助プログラム
  examples/                経路JSON
  docs/                    仕様と対応表
```

上記は実装済みの構成。MODの描画接続は各版の `client/` と `client/mixin/` に置く。

ForgeとNeoForgeはMDK由来の独立したビルドを使い、Gradle Wrapperは検証済みの8.8へ固定する。ビルドプラグインとJDKは版別に選ぶ。共通Java部分は各ビルドのサブプロジェクトとして解決し、完成JARに組み込む。別途core JARの配置は不要。

1.0.3の通常ビルドは音声ヘルパーをビルド・同梱しない。JDK 17と21を用意し、`scripts/build.ps1 -Release -SkipTests`でテストを実行せず`dist/1.0.3/`向けにassembleする。音声ヘルパーを必要とする利用者だけが`native-audio/windows/build.ps1`を別途実行する。この専用スクリプトにはVisual Studio C++ツール・Windows SDKが必要で、C++のタイムライン検査も実行する。

Forge 1.20.1はJava 17、NeoForge 1.21.1はJava 21を使う。ローダーとMinecraftの版を同時に固定し、Forgeの`1.20.x`ブランチを`1.20.1`と同じものとして参照しない。[Forge開発準備](https://docs.minecraftforge.net/en/1.20.1/gettingstarted/)、[NeoForge開発準備](https://docs.neoforged.net/docs/1.21.1/gettingstarted/)、[1.21.1用ModDevGradle MDK](https://github.com/NeoForgeMDKs/MDK-1.21.1-ModDevGradle)

同じリポジトリーにするが、`net.minecraft.*`を参照するカメラ・画面・イベントコードは版別にする。Minecraftの異なる版を対象に、一つのMinecraft依存commonソースがそのまま通るとは想定しない。初版はArchitectury等の実行時依存も必須にしない。

## 2. 主要クラスの責務

| クラス・境界 | 役割 |
| --- | --- |
| `ShotDefinition` | 地点、視線、実撮影秒数、録画倍率`playbackSpeed`、ディメンション、schemaVersion |
| `ShotEditor` | 1始まりの地点追加・上書き、座標・角度検証、既存IDとショット設定の維持 |
| `CameraCommands` | クライアントの `/wac cam`・`/wac goto` 登録。GUIと共通の編集中ショットを編集 |
| `CameraPose` | double XYZ、yaw/pitch、FOV。ゲームのEntityとは分離 |
| `PathSampler` | 実時間の秒数と経路から連続したCameraPoseを求める。録画倍率を経路時刻へ掛けない |
| `WaCameraClient` | プレビュー、準備、録画、終了の状態遷移 |
| `RecordingClock` | 単調増加時計、開始時刻、出力フレーム番号 |
| `DualPassRenderer` と版別Mixin | 撮影用Camera・可視チャンク・描画先を独立させ、通常描画の状態を復元 |
| Forgeの`WaCameraMixinPlugin`／`VanillaLevelRendererMixin` | バニラ専用の地形描画フックを分離し、Embeddium等の置換描画と競合しないよう適用を選択 |
| Forgeの`EmbeddiumCompatibility` | 撮影前後に地形の可視性を更新し、両視点で各viewport・FOVを反映 |
| Forgeの`ShaderCompatibility` | Oculus/Iris系の実際のシェーダーパック利用状態とAPIの利用可否を確認 |
| Forgeの`ShaderCapturePipeline` | 撮影専用のgbuffer・影・履歴・地形プログラムを持つOculusパイプラインを選択し、通常側を復元 |
| Forgeの`ShaderCaptureState` | 撮影用のフレーム時計を保持し、共有する描画・影・uniformの状態を退避・復元 |
| Forgeの`WindowMixin` | 撮影中のシェーダー最終描画へ録画ターゲットの幅・高さを返す |
| Forgeの`DistantHorizonCaptureBuffers` | DH 2.3.4の撮影用FBO・色／深度テクスチャ等を通常画面から分離して管理 |
| NeoForgeの`WaCameraMixinPlugin`／`VanillaLevelRendererMixin` | バニラ用のチャンク描画フックをSodium導入時に外し、置換描画との競合を避ける |
| NeoForgeの`SodiumCompatibility` | 撮影前後に地形の可視性を更新し、二視点のカメラとFOVを反映 |
| NeoForgeの`ShaderCompatibility` | Irisの利用状態を確認し、シェーダー有効＋DHの未対応構成を拒否 |
| NeoForgeの`ShaderCapturePipeline`／`ShaderCaptureState` | Iris 1.8.12向けの独立gbuffer・影・履歴・Sodium programsと、共有状態の退避・復元 |
| NeoForgeの`WindowMixin`／Iris用Mixin | 撮影時だけ録画サイズと独立Cameraの情報をシェーダーへ渡す |
| `GlFrameCapture` | 撮影用FBOの画像をPBO経由で読み出す。OpenGL操作のみ |
| `CfrTimeline` | 実撮影時刻を倍率付きの出力スロットへ対応させ、固定出力fpsの順序にする |
| `RecordingOptions` | 出力解像度・fps、実撮影秒数、録画倍率。取得fpsと最大出力枚数を計算し、1倍超の音声を無効化 |
| `FfmpegRecorder` | 子プロセス、入力pipe、ログ、終了・異常検知 |
| `AudioCapture` | OS別音声取得、開始時刻・サンプル時計の報告 |
| `RecordingFinalizer` | 音声時刻補正、MP4結合、検査、ファイル確定 |
| `ShotRepository` | 件数制限のない名前付きショットの保存・読み込み |
| `ShotPatternRepository` | 名前をパスに使わず、1〜10の固定スロットへショットを保存・復元 |
| `ShotJsonStorage` | 二つの保存方式で共有するJSON検証、schema移行、原子的な置換保存 |

ゲームの可変オブジェクトをエンコードスレッドへ渡さない。カメラ姿勢、時刻、画像バッファーの所有権を明示した小さなデータとして受け渡す。

## 3. カメラの先行試作

本人を通常の操作対象・カメラEntity参照として維持し、**録画用の追加ワールド描画と、通常プレイ画面の描画を分離する**。録画用描画の間だけ独立Camera・FOV・専用の深度付きフレームバッファーを使い、本人モデルを描画する。通常プレイ画面は元の一人称・手・照準・HUDを維持する。本人の移動、移動パケット送信、ゲームモード、実座標は変えない。

追加描画は通常のワールド描画より前に実行し、通常描画がプレイ用のCamera・射影・描画状態を再構築する。画像取得頻度 `出力fps / playbackSpeed` に合わせて追加描画を間引き、表示フレームすべてで二重描画する必要をなくす。ゲームtickと入力判定を余計に進めず、録画の視点でクリック判定を上書きしない。

Minecraftの可視チャンク一覧は一視点用のキャッシュを持つ。バニラ描画では撮影側に独立したfrustumと読み込み済み描画チャンクから一覧を作り、通常側の非同期チャンク構築・可視性キャッシュを汚さない。単にCameraとFBOを交換するだけでは十分ではない。

描画ターゲットの再バインド、自己表示、透明描画、投影行列、GL状態、例外時の復元を版別Mixinで処理する。通常のFabulous合成ターゲットはプレイ画面に結びついているため、バニラ描画の撮影側ではFancy相当の経路を使う。ユーザーの画質設定そのものは変更しない。シェーダー有効時は、以下の版別の独立パイプラインを使う。

alpha.4のForge版では、Embeddium 0.3.31による`renderChunkLayer`の置換と、WaCameraの`resortTransparency`呼び出しへのRedirectが競合する起動失敗を修正した。`setupRender`・`compileChunks`・透過面ソートのバニラ専用処理を`VanillaLevelRendererMixin`へ分け、Embeddium／Rubidium／Sodium系の描画MODがある場合は適用しない。描画先の退避・復元、アウトラインやデバッグ描画の抑制などの基礎的な処理は残す。

Embeddium経路では撮影前と撮影後の`finally`で地形の可視性を無効化し、それぞれの通常`setupRender`に対応するカメラ・viewportから再計算させる。位置と向きが同じでもFOVだけ異なる二視点を扱うため、位置の変化検知だけに依存しない。可視リスト内部は可変領域や構築キューを参照するので、浅いコピーによる保存復元は行わない。互換APIを解決できない場合は録画開始前に理由を表示する。対象にしている実機構成はForge 47.4.10＋Embeddium 0.3.31＋Oculus 1.8.0であり、他の派生MODや版まで確認済みとは扱わない。

### Forgeのシェーダー録画

`ShaderCapturePipeline`は現在のシェーダーパックから撮影用の`IrisRenderingPipeline`を生成する。gbuffer、影の描画先、TAA等の履歴、Embeddiumの地形シェーダーの差し替えを撮影側で保有し、描画中だけPipelineManagerの現在値とディメンション別の参照を入れ替える。ワールド描画後は合成と色変換を完了してから画素を取り出す。生成失敗を通常側のシェーダー全体を無効化する経路へ渡さず、録画側のエラーとして扱う。パック・ディメンション・通常パイプライン・再読込世代が変われば撮影側を作り直し、停止時には所有する資源だけを破棄する。

`ShaderCaptureState`は撮影用のフレームカウンターと時計を継続して持つ。撮影前にはOculusの共有描画状態、影の行列・可視情報、WorldRenderingSettings、LevelRenderer内のバッファー参照を退避する。撮影後の`finally`で通常側へ戻し、uniform・samplerのキャッシュを解除する。Shader Storage Bufferの結び付けもパイプラインの構築・描画・破棄をまたいで復元する。別カメラの過去フレームや描画状態を通常画面へ混ぜないことが目的である。

シェーダーの最終合成はウィンドウの幅・高さを参照するため、撮影中に限り`WindowMixin`から録画ターゲットの大きさを返す。描画前には通常画面のscissorを無効化し、終了時に元のscissor・viewport・FBOを復元する。これにより寸法が異なる場合に画面の一部しか描かれず黒い余白が生じる問題を修正した。960×600の操作画面と1280×720の録画を使い、昼夜とも録画画像に黒余白がないことを確認した。

Distant Horizonsとの連携では、描画前のフレーム処理を通常側で行い、DHのシェーダー・FBO・frustumの優先順位付き登録を撮影中だけ切り替えて復元する。追加の`DistantHorizonCaptureBuffers`はDH 2.3.4のキャッシュ寸法、プログラム、インデックスバッファー、FBO、色／深度テクスチャを描画ビューごとに保持する。異なるサイズの二視点でDHが繰り返し資源を作り直すことを避け、撮影終了時には撮影側の資源だけを解放する。地形データとその管理バッファーは共有したまま破棄しない。DH 2.3.4-bを併用した昼夜の実ゲーム録画に成功しているが、長時間の資源使用量は追加検証が必要である。

Forge 47.4.10＋Embeddium 0.3.31＋Oculus 1.8.0＋DH 2.3.4-b＋Complementary Unbound r5.6で、昼夜各8秒・240フレームの録画と通常プレイの維持を確認した。これはalpha.4時点の実施記録で、他のパックやMOD全体の互換性を保証しない。

### NeoForgeのシェーダー録画（1.0.1）

対象はMinecraft 1.21.1用のIris 1.8.12と、その配布版が指定するSodium 0.6.13。実JARを`javap`で調べ、公開APIだけでなく、反射で扱うフィールド・メソッドも照合した。Irisの1.21.1ブランチの最新ソースは後続版向けのため、1.8.12公開前のcommit `b4b2c22c`のソースを参考にし、JARのシグネチャとバイトコードを優先する。外部MODのクラスは任意依存として反射で解決し、シェーダーなしの録画でIris・Sodiumを必須にしない。

`ShaderCapturePipeline`は撮影専用の`IrisRenderingPipeline`を直接生成し、描画中だけ現在のpipelineとディメンション別の参照を交換する。gbuffer・影・TAA等の履歴を通常側と分け、LevelRendererの合成後に色変換を完了する。Iris 1.8.12は各pipelineが`SodiumPrograms`を所有し、地形描画時に現在のpipelineから取得するため、Forgeの旧地形プログラム差し替え方式は使わない。Sodiumの可視性は撮影前後に更新する。

`ShaderCaptureState`と版別Mixinで撮影時計・カメラuniform・共有描画状態を切り替え、通常画面へ復元する。撮影中だけウィンドウ寸法の参照を録画ターゲットへ合わせる。Shader Storage Bufferのindexed binding範囲も退避・復元する。Iris 1.8.12の`ACTIVE_BUFFERS`は共有レジストリーなので丸ごと置き換えず、撮影が所有するバッファーだけをidentityで登録から外し、撮影側の終了処理で解放する。

停止・再作成時は撮影所有のpipelineを破棄し、Iris 1.8.12の通常の`destroy()`で残るbegin/setup/shadow compute、色変換、Sodium programも有効状態を調べて解放する。constructor途中の失敗では生成したpipeline参照を取得できないため、登録済みSSBOの差分は回収するが、部分生成された全GPU資源の回収までは保証できない。

NeoForgeのDH用二視点バッファー分離は実装しない。Irisのシェーダーが有効でDistant Horizonsも導入されている場合は、理由を表示して録画開始を止める。シェーダー無効時はこのガードを適用しない。Iris APIの不一致や描画中の失敗も録画側のエラーとして処理する。

以上は実装と静的なAPI照合の記録である。利用者の希望により1.0.1ではMinecraft起動・自動テスト・実録画を行っておらず、NeoForgeでの画素・操作の維持・長時間のGPU使用量は未確認。Forgeの過去の録画結果をNeoForgeの実証として扱わない。

`Camera.setup`終了付近への限定Mixinと必要なAccessorを版別に実装する候補を検証する。角度・FOVの公式イベントで足りる部分はイベントを使う。自己モデルを描画する条件、カメラの独立判定、フラスタム、描画距離、視点揺れ、音声リスナーも確認し、描画中だけの一時的な変数書き換えに依存しすぎない。

自分を映すためにF5の視点設定を強制変更せず、録画用描画中の`Camera.isDetached`相当と自己モデルの描画条件だけを補正する。プレビューは一時的に画面を撮影視点へ切り替えるが、録画とは別の状態とする。

代理カメラEntityへ`setCameraEntity`する方式は採用しない。本人の入力、サーバーへの移動通信、ブロックやEntityのクリック判定を維持する。クリックの始点は本人の目であり、遠隔カメラではない。

確認したForge 1.20.1のパッチでは角度イベントはCameraのsetup後にあり、NeoForge 1.21.1ではCamera側にフックがある。呼び出し場所を同一とみなさず、採用するビルドの実ソースで順序を確認する。両版共通の角度イベント内でXYZも変更する実装は避ける。[Forge 1.20.1 GameRenderer](https://github.com/MinecraftForge/MinecraftForge/blob/1.20.1/patches/minecraft/net/minecraft/client/renderer/GameRenderer.java.patch)、[NeoForge 1.21.1 Camera](https://github.com/neoforged/NeoForge/blob/1.21.1/patches/net/minecraft/client/Camera.java.patch)

検証は、本人から離れた固定／移動カメラと、一人称の操作画面を同時に確認する。通常Cameraの位置・独立判定を検査し、本人の歩行・回転・ジャンプ・建築、インベントリー中の録画継続、終了後の状態を検証する。マルチプレイでの別クライアントからの確認は別途必要となる。

## 4. 経路の計算

地点はレンズ位置の絶対座標、角度はMinecraftのyaw/pitchに合わせる。GUIで「現在位置」を取るときは足元ではなく、現在の有効なカメラ姿勢を登録する。JSONのサンプルは`examples/intro-shot.json`を参照。

- 一地点：固定位置・固定または追尾の向き。
- 二地点：線形補間。
- 三地点以上の「なめらか」：centripetal Catmull–Romを候補にする。端点は専用処理し、同位置の連続点によるゼロ除算を防ぐ。
- なめらかな経路は事前に弧長の近似テーブルを作り、時間を距離へ対応させる。地点間隔で急に速度が変わることを防ぐ。
- 登録時の向き：yawを最短の回転方向に展開し、pitchとともに補間。初版のrollは0固定。
- 自分・指定座標を見る：カメラ位置から注視点へlook-atを計算。極端な上下や同一点でもNaNを返さない。
- 全点同位置の場合：固定撮影として扱う。向きが異なる登録点は時間で向きを変える。位置の重複削除で意図した回転まで消さない。
- プレビューや撮影の描画時に実時間の時計から位置を評価する。カメラを20Hzのtickだけで移動させない。

`durationSeconds`は経路と実撮影の長さであり、`playbackSpeed`を掛けたり割ったりして`PathSampler`へ渡さない。倍率を変更しても通常プレイとプレビューの経路速度は変わらず、完成動画の時間軸と追加描画の頻度だけが変わる。曲線は壁を避ける保証を持たないので、プレビューで確認する。

## 5. 映像の取り出しとエンコード

```text
描画スレッド
  取得fps＝出力fps÷録画倍率に応じて追加描画の要否を判定
    → 撮影用Camera・frustum・FBOを有効化
    → HUDと一人称の手を含まないワールドを描画
    → 固定サイズの録画FBOへコピー／縮小
    → PBOリングへreadbackを指示（取得時刻を記録）
    → 撮影用の状態をfinallyで解放
  通常の一人称ワールド・手・HUDを描画
    → 操作用REC表示を追加

後続フレームの描画スレッド
  GPU完了を確認 → 上限付きCPUバッファーへコピー

録画スレッド
  実撮影時刻を倍率付きの出力スロットに並べる → FFmpegのstdin → 一時動画

音声補助プログラム
  1倍かつ音声ONのみ：MinecraftのPIDを指定 → 時刻付きPCMを一時保存

停止後の保存スレッド
  動画＋必要な場合だけ時刻補正した音声 → 完成MP4 → 検査 → 保存成功
```

描画スレッドからFFmpegへの書き込み、ディスクI/O、音声の結合を行わない。GLオブジェクトの作成・読み出し・破棄はGLコンテキストを持つ描画スレッドに限定する。

第一段階の画素取得は同期readbackでもよい。連続録画の製品版では3枚程度のPBOリングとfenceを検証する。PBOを発行した直後に待ってmapすると非同期化の利点が消える。[KhronosのPBO解説](https://wikis.khronos.org/opengl/Pixel_Buffer_Objects)

Forgeの`AFTER_LEVEL`は手の描画前であり、あらゆるポスト処理を終えた最終画像の保証にはならない。録画の画素は通常の画面から取得せず、追加ワールド描画が完了した専用ターゲットから取得する。シェーダーMOD対応は個別に検査する。[Forgeの描画順](https://github.com/MinecraftForge/MinecraftForge/blob/1.20.1/patches/minecraft/net/minecraft/client/renderer/GameRenderer.java.patch)

画素フォーマット・行の詰め方・上下反転・色の範囲・出力の偶数寸法を固定する。UIだけ消えていても、色や上下が間違っていれば不合格とする。1080pのRGBAは約7.9MiB/枚、1倍の30fpsで約249MB/秒、60fpsで約498MB/秒の転送量になる。倍率が大きい場合は実時間の取得頻度を下げるが、一枚分の追加描画の重さは残る。操作が簡単でも、録画負荷が必ず軽いとは表現しない。

フレームバッファーは解像度に比例した上限を設定し、初期案ではMODが持つ録画用GPU/CPUバッファー合計128MiB以内を目標に設計する。エンコーダーやゲーム本体のメモリーはこの数字に含まれず、別途測る。

## 6. フレーム落ちと時刻

rawvideoは画素列であり、各フレームの実時刻を持たない。`-framerate 30`で入力すれば、入力された30枚が動画の1秒として扱われる。alpha.5では取得時刻を倍率に応じたスロットへ対応させ、通常撮影の処理落ちと意図した倍速録画を区別する。[FFmpeg rawvideo仕様](https://ffmpeg.org/ffmpeg-formats.html#rawvideo)

実撮影時間をD秒、出力fpsをF、倍率`playbackSpeed`をS（1〜120の有限数値）とする。小数を丸めて整数fpsにせず、取得頻度は `F / S`、取得間隔は `S / F` 秒で計算する。例えば24fps・10倍は2.4fpsの取得になる。品質は720p24／720p30／1080p24／1080p30／1080p60を選択でき、初期値は720p30。

1. 録画準備と最初の有効フレームの確保後に、共通の開始時刻T0を決める。
2. `System.nanoTime()`等の単調時計から、出力スロットnに対応する実撮影時刻を `T0 + n × S / F` として求める。FFmpegへ渡す出力fpsはFのままにする。
3. 描画した時刻を保持し、GPU転送の完了時刻を撮影時刻として扱わない。
4. 固定された短い許容遅延内でスロットに対応する画像を選ぶ。間に合わないスロットには直前画像を複製する。
5. 実時間でD秒の指定撮影を完走した場合は `ceil(D × F / S)` 枚を出力する。動画の長さは `ceil(D × F / S) / F` 秒で、理論値D/Sとの差は1フレーム未満となる。最小1フレームで、途中停止時は実際の停止時刻から同じ換算を行う。
6. 複製は失われた動きの復元ではない。動画の長さを保つための処理であり、該当箇所は静止して見える。
7. エンコーダー自体が継続して実時間に追いつかない場合は停止する。キューだけを増やして解決しない。

エンコーダー遅延の上限は初期案2秒。遅延判定は大きな画素キューを保持せず、スロット番号と処理済み番号から計算できる。録画停止後に処理済み範囲を確定し、音声を使用する1倍では音声も同じ終了時刻で仕上げる。性能不足で短くなった場合は正常な全区間保存と表示しない。

低TPSでも指定した実時間を撮る。例えば60秒・10倍なら撮影は60秒続け、完成動画は約6秒になる。ゲーム内tick数や倍率を根拠に実撮影時間を変更しない。ゲームが実際に一時停止した場合は保存へ進む。インベントリーやチャットなどゲームを停止しない画面では裏の録画を継続する。

倍速では実撮影時点から取得枚数を減らす。等倍の大きな動画を録った後に再エンコードして縮める方式ではない。出力は可変ビットレートで内容にも左右されるため、10倍時の容量が厳密に10分の1になる保証はしない。回復用のセッション情報にも倍率・取得fps・要求した動画長を保存し、既に倍率を反映した映像へ二重に速度変換をかけない。

## 7. 音声の技術試作

現在の導入方法はヘルパーの手動指定に限定する。新規設定は無音。等倍で音声が有効なら、録画開始前に設定された絶対パスの実行ファイルを検証し、未設定・不正・不存在は理由付きエラーにする。検証や起動に失敗しても音声OFFへ自動変更して録画を続行しない。MODによる抽出・取得・更新はなく、旧版の設定とヘルパーはそのまま利用できる。

音声補助プログラムを起動するのは `playbackSpeed == 1` かつ音声設定が有効な場合だけとする。1倍超では`RecordingOptions`側でも音声を無効化し、音声の時間伸縮や倍速結合は行わない。GUIの音声設定は上書きせず、1倍へ戻したときに元の選択を使えるようにする。

Windows用の小さなC++補助プログラムからapplication loopbackを使い、Java側は`ProcessHandle.current().pid()`で対象を渡す。通信プロトコルは開始準備、開始、停止、異常、サンプル形式、時刻情報に限定する。FFmpegでプロセス単位取得が当然にできるとは想定せず、取得部分を別責務にする。

Microsoft公式サンプルの最低要件はbuild 20348以降。Windows 11 x64を初期の検証対象とし、起動時に実際のAPI利用可否も調べる。通常のWASAPI endpoint loopbackは他アプリの音を含み得る別方式なので、自動フォールバックしない。[公式サンプル](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)、[通常loopbackの説明](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)

最初は48kHz・ステレオのPCM sidecarへ保存し、停止時にAACへ変換・映像に結合する。二本のライブpipeの起動順やブロックを同時に解決するより、時刻を検査しやすい。16bit PCM換算で約11.5MB/分の一時容量が追加で必要になる。実デバイス形式に応じた変換は明示する。

音声開始のオフセット、音声サンプル位置、native側の単調時刻を記録する。JavaのnanoTimeとnativeの時刻は、起点や単位が同一だと仮定せず、往復ハンドシェイク等で対応を測る。長時間はサンプル時計のドリフトも計測し、無音補完・先頭トリム・リサンプルで共通時計に合わせた音声を作る。メタデータなしのPCMに`aresample=async`を付けるだけで実時計との差が解決するとは扱わない。

音源の空間的な聞こえ方は初版では本人基準に固定する。Cameraを差し替えた影響でリスナーまで動かないか、音の距離減衰を実機で確認する。

プロセス単位loopbackが取得するのは、既にミックスされた出力であり、取得後に聞く位置を変更できない。本人基準にする処理は音が出る前の`SoundEngine`リスナー更新に置き、位置と向きの両方を本人に合わせる。撮影終了後は元の更新経路へ戻す。

将来のクロスOS候補はOpenAL Softの`ALC_SOFT_loopback`。ただし既存の音の横取りではなく出力デバイスの代替なので、通常のスピーカー再生、サンプル生成の駆動、再初期化も設計する必要がある。[OpenAL Soft拡張仕様](https://openal-soft.org/openal-extensions/SOFT_loopback.txt)

## 8. FFmpegと保存

既存FFmpegの実行ファイル指定と、「FFmpegを準備」による固定版の取得を提供する。FFmpeg・ffprobeはJARに同梱せず別プロセスとして起動する。準備ボタンはGyanの9.0.2 essentialsを固定SHA-256で検証し、LICENSE・README・取得元を記したORIGINとともに配置する。1.0.3でもこの機能は維持し、音声ヘルパー用の自動取得は追加しない。

ソフトウェアH.264を基準実装とし、NVENC/QSV/AMF等は利用可能一覧に存在するだけで有効にしない。短い実エンコードを実施し、失敗時は撮影前にソフトウェアへ切り替える。エンコーダーごとに異なる品質引数を内部で吸収し、GUIにはCRFやGOP等を出さない。

Javaの`ProcessBuilder`へ引数リストで渡す。シェル文字列を組み立てず、日本語・空白入りパスもそのまま一引数として渡す。stderr/stdoutは別途読み続け、pipeが詰まらないようにする。終了時は入力を閉じ、終了コードを取得する。タイムアウト時は異常保存へ移る。

記録中はfragmented MP4を一時ファイルへ書き、停止後に音声を合わせて通常MP4へ仕上げる案を採る。映像は再エンコードせずコピーし、音声だけAACへ変換する。fragmented MP4は通常MP4より中断時の読出しに向くが、すべてのクラッシュから完全回復する保証はない。[FFmpeg fragmentation](https://ffmpeg.org/ffmpeg-formats.html#Fragmentation)

各セッションはUUID付きの作業ディレクトリーに一時映像・音声・時刻情報・設定・エラーログを保存する。完成ファイルはffprobeでストリームと長さを検査し、同一ボリュームで確定名に変更した後に「保存成功」を通知する。回復用データは成功確認前に消さない。中断・不完全ファイルを成功した動画と混同しない。

1.0.2では、利用者が不要と判断して確認画面で削除を確定したセッションを、回復一覧から個別に削除できる。映像断片・音声・時刻情報・ログと、そのセッションに属する失敗した回復処理の一時データを対象とする。完成したMP4、他のセッション、`wacamera/patterns/`と`wacamera/shots/`は対象外とする。使用中のセッションは削除しない。失敗時はエラーを表示し、残った対象を再試行できるようにする。これは利用者の明示操作による破棄であり、保存成功前の自動削除を行うものではない。

空き容量の検査は完成動画だけでなく、一時動画、PCM、仕上げ中の完成MP4が同時に存在する最大量を見込む。可変ビットレートでは厳密な事前予測に頼らず、録画中にも空き容量を監視する。

配布時は採用するFFmpegビルドのライセンスと構成を記録する。libx264等を含むビルドではGPL条件になるため、必要な告知・ライセンス・対応ソース提供方法を配布設計に含める。「別プロセスなら配布上の確認不要」とは扱わない。[FFmpeg公式のライセンス説明](https://ffmpeg.org/legal.html)

Flashbackは独自ライセンスなので、公開ソースがあることを流用許可とみなさない。この案のカメラ・録画処理は一般的な技術を用いて独自実装する。[Flashback LICENSE](https://github.com/Moulberry/Flashback/blob/master/LICENSE.md)

## 9. 状態管理と復元

```text
IDLE → PREVIEW → IDLE
IDLE → PREPARING → COUNTDOWN → RECORDING → FINALIZING → IDLE
```

各状態で停止要求を受けられる。例外でも、視点・FOV・HUD・入力・音声リスナーを解放する経路を一つに集約する。画面の復元とファイルの仕上げは切り離し、FINALIZING中にも普通のゲーム操作へ戻れるようにする。初版は仕上げ中の二重録画開始を受け付けない。

設定を広範囲に書き換えて戻すより、撮影モードの有効期間だけ描画判断を上書きする。復元する値が必要なら開始時に保存し、終了処理を複数回呼んでも壊れないようにする。切断後に古いplayerやlevelへアクセスしない。

## 10. UIと保存形式

Minecraft標準のScreen・Button・EditBox・一覧部品で作る。最初から外部UIライブラリーを必須にせず、キーバインドは両ローダーの登録方法に合わせる。GUIの重複コードは短く保ち、画面の状態と入力検証を共通Javaに置く。

ショットJSONと録画環境の設定は分ける。経路JSONにGPU名やPC固有のFFmpegパスを入れない。画質と音声の選択も録画環境側に保持する。ショットには名前、ディメンション、地点のXYZ・yaw/pitch・順序、視線と注視座標、FOV、補間方法、撮影秒数、カウントダウン、`playbackSpeed`を含める。

`ShotDefinition.CURRENT_SCHEMA_VERSION`は2。canonical constructorの末尾に`double playbackSpeed`を追加し、1〜120・有限を検証する。旧11引数constructorは互換用に残し、schema 1を渡された場合もschema 2・1倍へ変換する。`ShotEditor`による地点追加・上書きは倍率を含む他の設定を保持する。

`ShotJsonStorage`はJSONの形と型を検証してからrecordへ変換する。schema 1のJSONはメモリー上でschema 2・`playbackSpeed: 1`へ移行し、schema 2はこのフィールドを必須とする。未指定を0倍として受け入れず、0、範囲外、NaN/Infinityや文字列の数値を拒否する。未知の版、空リスト、過大地点数、無効ディメンションも拒否する。読込時の自動書き戻しは行わない。

`ShotPatternRepository(Path)`は`SLOT_COUNT = 10`とし、`save(int, ShotDefinition)`、`load(int)`、`list()`を提供する。`list()`は`Slot(number, name, occupied)`を番号順に全10件返し、空枠は名前を空文字にする。番号は1〜10だけを受け付け、名前をパスへ組み込まず `wacamera/patterns/pattern-01.json` 〜 `pattern-10.json` に保存する。壊れたファイルを空枠として隠さず読込エラーにする。

GUIの「パターン」タブではA（1）〜J（10）の枠を選択する。保存済み枠の上書きは確認し、保存内容の呼び出しも現在の編集と異なる場合は置換を確認する。キャンセルで編集中の内容を維持し、了承後に全フィールドを編集画面へ復元する。呼び出しは本人の移動や録画開始を伴わない。従来の`ShotRepository`と`wacamera/shots/`の名前付き保存は件数制限なく残す。

両repositoryの書き込みは共通helperで同じディレクトリーの一時ファイルへUTF-8 JSONを書き、`FileChannel.force(true)`後に`ATOMIC_MOVE + REPLACE_EXISTING`で置換する。原子的な移動ができない場合は例外とし、既存設定を残す。異なる枠に同じ保存名を付けても相互に上書きしない。

共通の経路は両版で読み込める。ただし、MOD固有のディメンションIDがもう一方に存在する保証はない。ワールドとの紐付けはローカルの一覧管理で持ち、経路の共有時にサーバー接続情報を含めない。

| P3 | バッファー上限、CFR、PBO、異常処理 | 意図的な処理落ちで長さが縮まず、メモリーが増え続けない |
| P4 | Windows音声補助、時刻補正、MP4結合 | ゲーム音が入り、別アプリ音が混ざらず同期目標を満たす |
| P5 | カジュアルUI、なめらかな経路、自分を向く、導入支援 | GUIで地点設定から動画保存まで完結。音声は外部ヘルパーの事前設定が必要 |
| P6 | 両版の実機検証、対応表、リリース成果物 | クリーン環境に二本のJARをそれぞれ導入して同じ操作ができる |

二視点同時描画は必須機能として両版に含める。広いシェーダー互換、他OS音声、各種GPUでの性能測定は追加の検証範囲とする。初案の工数見積もりは二視点を外していたため、本仕様には適用しない。

最初の着手単位は「両版で自分を映す固定カメラ」と「Forge版で10秒の無音MP4」。UIを作り込む前に、入力・自己描画・フレーム取得の成立を確認する。

## 12. 検証方法

### 共通ロジックの自動テスト

- 経路の始点／終点、重複点、同位置回転、角度179度から-179度への短い回転、注視点との一致。
- 偽時計を使い、60Hz・30Hz・断続的な停止があっても1倍の10秒30fpsが300スロットになること。倍率付きは`ceil(D × F / S)`枚となり、24fps・10倍で取得2.4fpsと出力24fpsを混同しないこと。
- 停止要求の重複、準備失敗、エンコーダー異常、最終保存失敗で正しい状態へ遷移すること。
- JSON往復、schema 1から1倍への移行、schema 2の倍率必須、版番号の不一致、破損データ、範囲外の数値。
- 全10スロットの再インスタンス後の復元、同名でも別枠を保護すること、日本語名、座標・向き・視線・FOV・経路・秒数・倍率の保持、1未満・10超の番号の拒否。
- 小数倍率、途中停止、1フレームへの量子化、倍速で音声補助を起動しないこと、回復処理で倍率を二重適用しないこと。

### 実ゲームの受け入れ試験

両版、シングルとマルチ、基準の同一ワールドで行う。画面描画と音声は通常の単体テストだけでは検証できない。

- 本人のスキン、装備、歩行、回転、ジャンプ、アイテム使用と通常の到達距離。
- 水中、暗所、雨、透明物、チャンク境界、遠景、ディメンション切替。
- HUD除外、画面と動画の色、上下、縦横比、サイズ変更時の終了。
- 10分録画で音と映像のずれ50ms以内を目標。長時間対応前に30分・60分へ拡張する。
- パルス音と画面フラッシュを同時に出す検証用シーンで、先頭と末尾のずれを測る。
- フレーム複製率、中央値とp95フレーム時間、エンコード遅延、録画前後のメモリーを比較する。
- ディスク不足、FFmpeg強制終了、切断、ゲーム終了から復旧でき、フォーカス喪失中は録画を継続できること。
- 音声試験ではMinecraft音と別アプリの音を同時に流し、取得対象の分離を確認する。

CIでは純Javaテストと両MODのビルドを行い、映像・音声・GPU依存部分は記録付きの実機試験で補う。すべてのMODパックに対応したと表現せず、検証済みの組み合わせを対応表に追加していく。
