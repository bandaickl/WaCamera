## 1. 提案する製品

**撮影地点を置き、撮影時間を決め、ボタン一つでカメラ移動と動画保存を開始するMOD。** 自分のキャラクターも通常のワールド内の姿として映す。

必須要件はForge 1.20.1 / NeoForge 1.21.1、座標指定、自分を映す、動画まで保存する、細かな編集を要求しないこと、および**一人称で通常プレイしながら別視点を裏で録画すること**。最後の要件を初案で任意機能に回したのは誤りであり、本版で修正する。

本MODは、事前に構図を決めたリアルタイムの映像を保存する。**撮影後に別角度で撮り直すことはできない。** リプレイ一覧、時間軸エディター、キーフレーム編集画面を経由せずに動画ができる。

## 2. 判断の前提

一人称操作と別視点録画の両立は確定した必須要件。その他の初期値は以下とする。

| 項目 | 推奨する初版 | 理由 |
| --- | --- | --- |
| 撮影中の画面 | 普段の一人称プレイ画面を維持し、別カメラの描画結果を録画 | 建築・冒険の操作性を保ったまま自分を撮影するため |
| 入力 | WASD・ジャンプ・マウスは本人を操作 | 自分で出演しながらカメラは自動移動できる |
| 音 | Windows x64の新規設定はON、既存の選択は保持。1倍超は無音 | Minecraft既存JNAとWindows標準APIで取得し、音声ヘルパーの導入を不要にする |
| 初期対応OS | Windows 11 x64 | 音声取得の実装範囲をまず一つに絞る |
| 対応ローダー | Forge 1.20.1、NeoForge 1.21.1の二本 | どちらも完成条件に含める |
| 導入場所 | クライアントのみ | 専用サーバーへの導入を必須にしない |
| 開発順 | 両版のカメラ試作 → Forge中心に録画 → NeoForge検証 | 最も危険な版差を早期に確認する |

プレイ用と撮影用の二視点を同じクライアントで描画する。録画側は専用フレームバッファーを使い、プレイ用のカメラ・手・照準・HUDを置き換えない。録画のためにゲームのtickを二回進めない。リプレイ方式でも後から別角度にできるが、リアルタイム二視点録画とは違う製品になる。

## 3. 最短の操作

1. キー設定から「撮影パネル」を開く。仮の既定キーはK、変更可能にする。
2. 好きな位置・向きで「現在の視点を追加」。またはXYZを直接入力する。
3. 次の位置で同じ操作を行う。地点は一つなら固定、二つ以上なら移動撮影になる。
4. 撮影時間を入力する。初期値10秒。必要なら「自分を向く」を選ぶ。
5. 「プレビュー」で構図を確認する。終了後は元の視点へ戻る。
6. 「別視点で録画」。3秒のカウントダウン後、撮影用カメラの経路移動と録画を同時に開始する。
7. プレイヤーは一人称のまま歩く・ジャンプする・建築するなど、通常の動作をする。
8. 時間終了または停止キーで裏の撮影を終える。操作画面は変わらない。動画フォルダーから結果を確認できる。

地点を置いた後は、本人を映したい位置まで移動して撮影を始められる。経路の作成にはクリエイティブ飛行が便利だが、サバイバルでも数値指定は可能とする。浮遊するカメラ操作用の自由移動モードは追加機能として後に回せる。

## 4. 最小公開版の機能

| 機能 | 仕様 |
| --- | --- |
| 撮影地点 | 1～64地点。追加、座標・向きの編集、順序変更、削除 |
| 地点コマンド | `/wac cam`で1から連番追加、`/wac cam <番号>`で現在視点を登録・上書き。続けてXYZ・yaw・pitchを指定すれば数値登録 |
| 地点へ移動 | `/wac goto <番号>`でサーバーの通常TPを要求し、本人の目線と向きを保存地点へ合わせる。チート／OP権限が必要 |
| 座標 | カメラのレンズ位置のXYZ。プレイヤーの足元座標と混同しないよう表示 |
| 視線 | 地点登録時の向き／自分を向く／指定座標を見る、の三種類 |
| 経路 | 直線／なめらか。二地点は直線、三地点以上で曲線を使う |
| 経路速度 | 経路全体の実時間の秒数を指定。通常はほぼ等速、細かな速度曲線は出さない |
| 撮影時間 | 初期10秒、1秒～60分。長時間は対応試験後に正式サポート |
| 録画倍率 | 1〜120倍、有限の小数可。初期1倍。実撮影時間は変えず、完成動画の長さを短縮 |
| 自分の表示 | 通常のスキン・装備・アニメーションを持つ本人を映す |
| プレビュー | 録画せずにカメラを再生。同じ経路・視線計算を使う |
| 録画 | MP4 / H.264、音ありならAAC。停止後の音声結合まで自動 |
| 品質 | 720p24／720p30／1080p24／1080p30／1080p60 |
| 画面表示 | 操作画面には通常のHUD・手・照準を残し、別視点の動画には入れない |
| 録画状態 | 経過時間と停止方法を操作画面に表示。REC表示は動画へ焼き込まない |
| パターン | A〜J（1〜10）の固定10枠。任意の名前で撮影設定を保存・復元。上書きと異なる編集中設定の置換は確認する |
| 保存 | パターン用JSONと従来の無制限の名前付きショット保存を併存。動画は日時付きファイル名で保存 |
| 言語 | 日本語を最初から実装し、英語翻訳用キーも用意 |

実装した初期値は720p30。alpha.5で720p24／1080p24を追加した。プレイ画面の拡大画像ではなく、選択した解像度でワールドを別に描画する。負荷が高い場合は解像度や出力fpsを下げる。

録画ターゲットは16:9固定で、プレイ画面の縦横比から独立する。録画中にプレイ画面の大きさが変わっても録画用の大きさは固定する。

### 録画倍率と時間

実撮影時間をD秒、出力fpsをF、録画倍率をSとすると、画像取得と撮影用追加描画の頻度は `F / S` fps、完成動画の理論上の長さは `D / S` 秒とする。例えば24fps・10倍は実時間で2.4枚/秒を取得する。ゲーム速度・tick・入力・音の再生速度は変更しない。カメラ経路とプレビューはD秒の実時間で進む。

指定時間を完走した動画のフレーム数は `ceil(D × F / S)`、実際の動画の長さはその枚数÷Fとする。最小1フレームで、理論値との差は1フレーム未満。処理落ち時はこの倍速用の時間軸に対して画像を複製する。音声はSが1を超える場合に無効化するが、ユーザーの音声設定値は保持する。録画倍率を1へ戻したら元の音声設定を使う。

倍率に応じて取得画像数を減らすが、動画の容量は動き・圧縮率・品質に依存する。10倍なら容量が厳密に10分の1になる、といった保証はしない。

## 5. プレイヤーとカメラの振る舞い

- カメラ位置と本人の位置を分離する。カメラ移動のために本人をテレポートしない。
- 撮影中のマウスは本人の向きを変える。登録したカメラの向きをマウスで崩さない。
- WASDは本人の向きを基準に動き、プレイ画面と操作の向きは通常どおり一致する。
- 攻撃・ブロック設置・使用の判定は、本人の目線と通常の到達距離を使う。離れたカメラから操作距離を伸ばさない。
- 建築・攻撃・使用は通常の一人称画面で行う。撮影カメラから本人を外側から映す処理は独立させる。
- 「自分を向く」は本人の上半身を向く。自動的に後ろを追いかける機能とは別で、カメラ位置は登録経路どおりに動く。
- 追尾対象の位置は描画時の補間を使い、20tickごとの階段状の回転を避ける。対象とカメラが同一点なら直前の有効な向きを維持する。
- 揺れ・ダメージ傾き・疾走によるFOV変化は撮影用の描画だけ抑える。プレイ画面はユーザーの通常設定を維持する。
- カメラが壁に入る経路はプレビューで確認する。初版では障害物を自動回避しない。本人が壁の向こうに隠れたら通常どおり隠れる。

カメラを切り離しつつ本人を操作する構成には既存実装例がある。ただし、そのソースは対象版のAPI保証ではなく、操作判定やクリック処理の調査資料として使う。[Freecam公式](https://github.com/MinecraftFreecam/Freecam)

## 6. 音声

1.0.4ではMinecraft既存のJNA（1.20.1は5.12.1、1.21.1は5.14.0）からWindows標準のWASAPI process-loopbackへ接続する。音声ヘルパーEXEとパス入力は不要で、音声用の新しいEXE・DLLは同梱・ダウンロードしない。Windows x64の新規設定は音声ONとするが、保存済みのON/OFFは上書きしない。旧ヘルパーのパス値は参照せず、設定から削除せず、既存の実ファイルも自動削除しない。旧C++ソースは履歴参考として残し、現行MODの利用・ビルドには不要とする。

録画倍率1倍で音声を有効にした場合は、Minecraftのプロセスを指定して再生音を取得する。音声は録画時計に合わせ、停止時に映像と自動結合する。1倍を超える録画は無音とし、音声取得を開始しない。音を録るときは、プレイヤーのいる場所を基準に聞こえる音を既定とし、カメラ位置による聞こえ方の変更は後回しにする。

この方式で分離できるのは「Minecraftプロセスの音」。同じプロセス内で再生されるボイスチャットMODの音は入り得る。「効果音だけ・音楽だけ」のトラック分離はしない。別アプリの通話音やマイク入力を自動では収録しない。

対応環境はWindows 11 x64とする。音声ONで非Windows・非x64の場合やAPIの初期化に失敗した場合は理由を表示する。PC全体の音や無音へ自動的に切り替えず、利用者が無音を選んだ場合に録画する。[Microsoftのプロセス単位ループバック公式サンプル](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)

マイク、別トラック出力、macOS/Linux向けゲーム音は追加開発に分ける。動画作成用のFFmpeg・ffprobeの既存仕組みは維持する。旧ヘルパーが保存した音声・時計メタデータの回復互換も維持する。1.0.4の音声方式は実録音・実録画で未検証であり、従来方式の試験実績を新方式の動作保証には使わない。

## 7. 対応範囲と限界

- シングルプレイと、クライアント側のカメラMODを利用できるマルチプレイを対象にする。
- 撮影対象はクライアントが受信・保持しているチャンクとEntity。カメラ移動だけで遠くの世界が自動受信される機能は持たない。
- プレイヤーからの距離だけで安全判定しない。開始前に経路周辺の読み込み状況を検査し、録画中も未ロードへの進入を検知する。
- 未ロード領域がある場合は開始を止め、本人を近づけるなどの対処を表示する。録画中に未ロードへ入ったら、そこまでを保存して停止する。画面内すべての完全ロードを保証するものではない。
- 経路は一つのディメンション内に限定する。別ディメンションや別ワールドの設定は確認なしに自動実行しない。
- サーバー停止やゲームの処理落ちは動画にも現れる。リアルタイム録画なので、後から完全になめらかな動きを再生成できない。
- 最小公開版の基準はバニラ相当の描画。シェーダー、描画最適化MOD、大規模MODパックは個別の互換性試験で対応を広げる。
- alpha.4のForge版はEmbeddium併用時の起動競合を修正した。Forge 47.4.10＋Embeddium 0.3.31＋Oculus 1.8.0で、シェーダーパック無効時の二視点録画を確認している。
- Forge版ではシェーダー有効時も、撮影専用のパイプライン・影・描画履歴を使って別視点を録画する。上記の構成へDistant Horizons 2.3.4-bを追加し、Complementary Unbound r5.6を有効にした昼夜各8秒の720p30録画を確認した。960×600の操作画面と異なる録画サイズでも黒余白はなく、影・発光・操作中の本人が映る。
- NeoForge版では1.0.1からIris 1.8.12＋Sodium 0.6.13（Minecraft 1.21.1用）の独立シェーダー録画を実装する。gbuffer・影・履歴・地形プログラムを分離し、通常画面の状態を復元する。実JAR API・ソース照合までの確認であり、ゲーム内動作・実録画・性能は未検証。NeoForgeのシェーダー有効＋Distant Horizons併用は理由を表示して録画を開始しない。Iris・Sodiumはシェーダー利用時の追加構成で、通常録画の必須依存ではない。多数のMODを含むユーザー環境全体の検証は今回の修正に含まない。

## 8. 開始・中断・保存の仕様

| 状況 | 動作 |
| --- | --- |
| 撮影開始 | 保存先・空き容量・経路・エンコーダー・音声を検査し、準備成功後にカウントダウン |
| 通常終了・停止キー | フレーム受付を止め、視点を即時復元。保存処理は別スレッドで完了させる |
| プレビュー終了 | 視点だけ復元し、動画は作らない |
| ゲームの手動一時停止 | 実際にゲームが一時停止した場合に撮影を終了して保存。マルチプレイ・LAN公開中のEscメニューでは一時停止しないため録画を継続 |
| フォーカス喪失 | 録画準備・カウントダウン・録画は継続。プレビューは終了。録画対象状態だけ自動一時停止を抑制 |
| インベントリー・チャット | ゲームが一時停止しない画面では別視点録画を継続 |
| 死亡・切断・ディメンション変更 | 撮影を終了し、旧ワールドや旧Entityの参照を解放 |
| ForgeのOculus、またはNeoForgeの対象Irisでシェーダーが有効 | 撮影専用のシェーダーパイプラインで描画・合成した映像を録画。通常プレイ用の描画状態は復元する。NeoForgeの実録画は未検証 |
| NeoForgeでシェーダー有効かつDistant Horizons導入 | 未対応の組み合わせとして理由を表示し、録画を開始しない。録画中に検知した場合は撮影を停止 |
| 描画MODの互換API・シェーダー構築の失敗 | 理由を表示して録画開始を中止。撮影中の失敗では追加撮影を止め、取得済みデータの保存処理へ進める |
| エンコーダー停止・ディスク不足 | 撮影を止め、視点を復元。残った一時データと原因を表示 |
| 継続的な録画処理の遅延 | 無制限にメモリーを増やさず終了し、次回の画質を下げる案内 |
| MP4仕上げ失敗 | 回復用ファイルを残し、保存成功とは表示しない |
| クラッシュ後 | 次回起動時に残存セッションを検出し、回復可能か調べる。完全復元は保証しない |
| 不要な回復データの削除 | 「回復」で一件を選び、「この回復データを削除」から確認画面の「完全に削除」で確定する。選択データと失敗した回復処理の一時データを削除し、完成MP4・他の回復データ・撮影設定は保全する。使用中は拒否、失敗時は理由を表示して再試行可能。自動・一括削除は行わない |

保存場所はゲームディレクトリーの `wacamera/patterns/`、`wacamera/shots/`、`wacamera/recordings/`。パターンは `pattern-01.json` 〜 `pattern-10.json` の固定ファイルへ保存し、名前をパスに使わない。同じ名前でも異なる枠は別ファイルになり、指定した枠だけを置換する。撮影設定は同じディレクトリーの一時ファイルから原子的に置換し、保存が失敗した場合は以前のファイルを保全する。

「パターン」タブで枠を選び保存・呼び出しを行う。保存済み枠への上書き、および異なる編集中設定への復元では確認を挟む。保存・復元の対象は名前、ディメンション、全地点のXYZ・yaw/pitch・順序、視線モード・注視座標、FOV、経路補間、撮影秒数、カウントダウン、`playbackSpeed`。復元は本人のテレポートや録画開始を伴わない。画質・音声の選択・実行ファイルの場所など録画環境は別設定として維持する。従来の名前付きショット保存には10件制限を適用しない。

JSONは `schemaVersion: 2` とし、`playbackSpeed` を必須の有限数値（1〜120）とする。schema 1を読み込む場合は1倍のschema 2へ移行する。読み込みだけでは元のJSONを更新せず、次の明示的な保存時に新形式を書き出す。未対応の版、破損した保存ファイルや不正な数値はエラーとして扱う。

## 9. 初版後に追加する機能

優先順の案：周回・後方追従のプリセット、マイク、自由カメラでの経路作成、シェーダーパックの対応拡大・NeoForgeの実録画検証とDH連携、他OS音声。倍率指定によるタイムラプス録画はalpha.5に含む。NeoForgeへのシェーダー録画移植は1.0.1に含むが、ゲーム内検証は別途必要。

撮影後の視点変更、巻き戻し、ワールドの再現、複数カメラ編集は、リプレイエンジンが必要になるため別規模の機能として扱う。特にMOD固有の通信・Entity・ブロック状態まで再現する機能は初版に入れない。

## 10. 公開版の完成条件

1. 両対象版で、XYZ指定の固定撮影と三地点以上の移動撮影が動く。
   録画中の操作画面は一人称のまま、手・HUD・照準と本人の操作を維持し、動画側には別カメラから本人が映る。ブロック設置・破壊を含む試験で確認する。
2. 移動・回転・ジャンプする本人が、他クライアントからも正常に動いて見える。
3. 1倍の10秒撮影が30fpsなら300フレームになる。倍率Sでは `ceil(10 × 30 / S)` フレームとなり、処理落ちを理由にさらに無断で短縮しない。
4. Windows 11 x64の基準機で、追加音声ヘルパーなしのJNA方式で音声ONの720p30・10分録画を完了する。既存の音声選択を維持し、音声ONの非対応環境・初期化失敗を明確に拒否する。1080p30/60は個別に計測する。1.0.4更新ではこの実機試験を実施しない。
5. 動画と音声の開始ずれ・10分後のずれは、試験目標として50ms以内に収める。
6. 停止・死亡・切断・保存失敗のすべてで視点と入力を復元する。
7. MOD本体の録画用バッファーを上限管理し、長時間で増え続けない。外部エンコーダーのメモリーも別に測る。
8. 保存したMP4を一般的なプレイヤーで再生でき、HUDや撮影パネルが映り込まない。
9. 日本語・空白を含む保存パスでも動く。設定の読み直しと版をまたいだ読み込みを検証する。
10. 配布はローダー別の二つのJAR。実際に試したOS、ローダービルド、描画MODの組み合わせを明記する。
11. 10件のパターンを再起動後も呼び出せる。保存先をまたぐ上書き、座標や倍率の欠落を起こさず、旧schema 1は1倍で復元する。

これらは測定済みの実績ではなく、これから実装・検証する受け入れ基準。
